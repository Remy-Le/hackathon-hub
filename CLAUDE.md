# Hackathon Hub — marketing content repo

LinkedIn marketing content and content pipelines for Hackathon Hub. No app code — this repo is copy, HTML/image assets for social graphics, and small Node scripts that render those graphics.

## Weekly roundup pipeline ("New hackathons in Europe")

A recurring LinkedIn post + matching visual carousel, published roughly weekly, covering newly-published hackathons across Europe grouped by region/country. The raw roundup now arrives pre-split into one raw paste per region (DACH, Western Europe, Northern Europe, Southern Europe, Central & Eastern Europe, Southeast Europe, plus one-off blocks like Online/Remote or NASA Space Apps) rather than one pan-Europe paste, since a single region alone can be dozens of events.

Both deliverables below are consumers of one shared parse step, `hackathon-roundup-parse` (`.claude/skills/hackathon-roundup-parse/SKILL.md`): it takes one region's raw paste and produces `hackathon-spotlights/weekly-roundup-YYYY-MM-DD/<region-slug>/data.js`, plus a fidelity QA pass against the raw source. Every other skill below reads that `data.js` instead of re-parsing the raw text itself — the raw paste only ever gets parsed once per region, no matter how many of the four output files get built from it. If `data.js` doesn't exist yet for a region, the skill that needs it runs `hackathon-roundup-parse` first; a fresh raw paste for a region that already has a `data.js` is a refresh request (re-parse, overwrite).

For one region's carousel, use the `hackathon-roundup-pipeline` skill (`.claude/skills/hackathon-roundup-pipeline/SKILL.md`): it ensures `data.js` exists (via `hackathon-roundup-parse`), builds that region's carousel, publishes it as a review artifact, and runs a carousel-rendering QA pass (raw-source fidelity was already checked once, during parsing). It is carousel-only — it does not touch the text post. The steps are also documented here for reference.

Two separate deliverables come from the same `data.js` — keep them in sync but don't conflate their formats. Run the text-post skills below whenever you want `post.md`/etc. for a region, and the `hackathon-roundup-pipeline` skill whenever you want that region's carousel; both can run independently once `data.js` exists, in either order.

Once a region's text post is rendered, use `hackathon-roundup-schedule` (`.claude/skills/hackathon-roundup-schedule/SKILL.md`) to actually schedule it to Buffer/LinkedIn: it picks the right text variant (`post.md` bold-stripped, `post-compact.md`, or `post-compact-single.md`) for LinkedIn's 3,000-character post limit, builds a first-comment link list that fits LinkedIn's separate 1,250-character comment limit, and covers the Buffer MCP mechanics (channel/org selection, `edit_post` re-validation, the image-asset URL requirement).

1. **The text post** — raw bold-unicode LinkedIn text (flag emoji region/country headers, bulleted events). Before publishing a new one, run three skills, one per output file (each renders from `data.js`, invoking `hackathon-roundup-parse` first if it doesn't exist yet for this region):
   - `hackathon-roundup-format-full` (`.claude/skills/hackathon-roundup-format-full/SKILL.md`) — renders the full post to `post.md` (not printed inline): bullet symbols, blank-line spacing, region/country headers, long-form tags.
   - `hackathon-roundup-format-compact` (`.claude/skills/hackathon-roundup-format-compact/SKILL.md`) — derives `post-compact.md` (locations and dates only, category tags dropped, special chips like 💰/🏨/🖥️/✈️ kept) in the same folder, plus a conditional `post-compact-single.md` when `post-compact.md` would exceed LinkedIn's 3,000-character limit.
   - `hackathon-roundup-format-regions` (`.claude/skills/hackathon-roundup-format-regions/SKILL.md`) — derives `post-regions.md` (region/country structure with hackathon counts only, no individual events) in the same folder.

   These three skills are the source of truth for the rendering rules; don't re-derive them (city/date/price/tag normalization itself lives in `hackathon-roundup-parse`, not here). All three write into `hackathon-spotlights/weekly-roundup-YYYY-MM-DD/<region-slug>/` for a single-region `data.js` (the normal case now) — the exact same per-region subfolder that region's carousel PNGs land in below, so two regions in the same week never collide on a shared filename. Only a `data.js` with more than one region in it (a full multi-region/pan-Europe parse) falls back to the flat dated-folder root (no single region to slug).

2. **The visual carousel** — a set of 1350×1350 PNGs (LinkedIn carousel format: one cover slide + one slide per region-page, "Option A" layout from `hackathon-spotlights/weekly-roundup-layouts.html`). `build-new-roundup.js` and `render-pngs.js` are generic, shared scripts — never edited per run — driven entirely by CLI args and the per-region `data.js` from `hackathon-roundup-parse`, so N regions can be built concurrently (separate sessions or subagents) with zero shared-file writes. Pipeline for one region:
   - `data.js` (from `hackathon-roundup-parse`) is a small CommonJS module exporting `{ week, regions, extraFlags }` (`regions` normally a single-entry array, tags stored long-form; `extraFlags` maps a country code to an already-fetched SVG path for a flag not yet in the base set, `{}` if none new this run).
   - Run `node build-new-roundup.js --data=<path to data.js> --out=<path>/carousel.html` → produces the standalone Option-A-only carousel page at `--out`. The region label ("`Europe`" when `regions.length > 1`, otherwise that single region's name), headline font size, brand/copy strings, `<meta>`/`<h1>`/intro `<p>` text, and the long-form-to-short-form tag conversion (`LONG_TO_SHORT_TAGS`/`shortTag()` in `build-new-roundup.js`) are all derived/handled at render time — nothing to hand-edit or grep-confirm afterward.
   - Publish the generated HTML as a per-region review artifact (favicon 🇪🇺) and check it before rendering PNGs.
   - Render to PNGs with `node render-pngs.js --html=<path to carousel.html> --outdir=<path>` (uses local `playwright` install in `hackathon-spotlights/` — Chromium must be installed once via `npx playwright install chromium`). Slide names are read from `window.__slideNames`, which `build-new-roundup.js` computes from `regions` (no hand-maintained array). PNGs land directly in `--outdir` — no separate staging folder or manual copy step.
   - **Important Playwright gotcha**: the review page ships zoomed to 0.42 (`.scaler{zoom:var(--z,.42)}`) and horizontally scrolled inside `.stage`. `render-pngs.js` reads the HTML at `--html`, string-replaces the zoom rule to nothing and strips the review chrome (`.wrap` max-width, `.stage` overflow, header/controls) *before* loading via `page.setContent`, so each 1350×1350 card lays out full-size from the first paint. Don't change zoom at runtime (via the `--z` var or an injected stylesheet) — Chromium doesn't reliably repaint backgrounds on a runtime `zoom` change and leaves stale page-background pixels behind the card edges. Screenshots render at `deviceScaleFactor: 2` → 2700×2700 PNGs.
   - Point `--out`/`--outdir` at `hackathon-spotlights/weekly-roundup-YYYY-MM-DD/<region-slug>/`, dated to the "published since" date named in that week's raw paste (not the render date) — that folder is both `data.js`'s home and the render destination.

Tag naming differs deliberately between the two deliverables: `data.js` (and therefore the text post) keeps long-form tags ("Artificial Intelligence (AI)"), the carousel visual converts to short-form tags ("AI") to fit the card layout, via `build-new-roundup.js`'s own `LONG_TO_SHORT_TAGS` table at render time. This is intentional, not an inconsistency to fix.

## Housekeeping

- `hackathon-spotlights/node_modules/` (from the local `playwright` install) is gitignored — don't commit it, just `npm install playwright` again if a fresh checkout needs it.
- `.agents/*.md` are marketing-skill context docs (ICP, positioning, etc.), not memory — static reference material, not auto-updated.
